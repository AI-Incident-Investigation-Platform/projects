# Устройство projects

## Граница сервиса

`projects` отвечает за то, кто есть кто в проекте: проекты, окружения,
сервисы наблюдаемого приложения, участники и роли, приглашения и
API-токены проекта. Пользователя знает только по `user_id`: профиль —
в `users`, вход — в `auth`.

Коннекторы мониторинга и репозитории сюда не входят: они уйдут в
отдельный сервис `integrations`. Там будут секреты клиентов, ключ GitHub
App и вызовы наружу в инфраструктуру клиента. Право управлять ими
(`integration.manage`, `repository.manage`) выдаёт роль в `projects`, а
`integrations` проверяет его так же, как любой другой сервис.

## Роли и права

Код проверяет только права (`Permission` в `src/core/db/enums.py`),
названия ролей — нигде, кроме назначения владельца при создании проекта.
Роль — строка таблицы `roles` с массивом прав. Встроенные роли заводит
начальная миграция:

| Право | owner | admin | developer | viewer |
|---|:-:|:-:|:-:|:-:|
| `project.read`, `report.read` | ✓ | ✓ | ✓ | ✓ |
| `investigation.run`, `review.write`, `incident.manage` | ✓ | ✓ | ✓ | |
| `repository.manage`, `integration.manage`, `api_token.manage`, `project.manage`, `member.manage` | ✓ | ✓ | | |
| `project.delete`, `ownership.manage` | ✓ | | | |

- Создатель проекта — owner. Глобальных ролей нет.
- Участник — строка `memberships (project_id, user_id, role_id)`.
  Пользователь живёт в БД `auth` и `users`, поэтому внешнего ключа на него нет.
- Не участник получает `404`, участник без права — `403`. Проверка —
  `ProjectAccess` в `src/core/access/`: одна выборка прав участника на
  запрос.

Правила управления участниками: назначить или снять можно только роль,
права которой целиком входят в права назначающего (`require_grantable` в
`ProjectAccess`); свою роль менять нельзя; в проекте всегда есть хотя бы
один участник с `ownership.manage` — при его снятии строки владельцев
блокируются, и параллельное снятие двух последних не пройдёт. Тогда admin
не трогает owner'а без особых случаев в коде — у него нет
`ownership.manage`. Выйти из проекта может любой участник, кроме последнего
владельца.

## Приглашения

- Зовут зарегистрированного пользователя по `user_id`; незарегистрированную
  почту не зовут. Фронтенд находит человека в `users` по юзернейму, почте
  или имени.
- `invite`: права и правила роли проверяются в БД, затем чтение
  закрывается (`rollback`), и `projects` спрашивает `users`
  (`GET /api/v1/users/lookup`) о приглашённом и приглашающем — с токеном
  приглашающего в `Authorization`, как велит SYSTEM.md. Пользователя нет —
  `422`, `users` недоступен — `503`, приглашение не создаётся.
- Запись — `invitations` со статусом `pending`; одно ждущее приглашение на
  человека в проекте держит частичный уникальный индекс. Истёкшее ждущее
  получает `expired`, когда его коснётся следующий запрос, и освобождает
  место новому.
- Письмо `projects.invitation` ставится в RabbitMQ после commit: оно только
  уведомление, сбой пишется в лог `invitation.letter_failed`, а
  приглашение остаётся во входящих (`GET /api/v1/invitations`).
- Ответ — под блокировкой строки приглашения; повтор того же ответа
  возвращает прежний исход. Принятие создаёт участника с ролью
  приглашения; уже участник остаётся со своей ролью.

## Проверка токена

Токен выпускает `auth`, `projects` проверяет его сам, без похода в `auth`
на каждый запрос:

1. Ключ подписи — по `kid` из JWKS `auth`
   (`http://auth.apps:8001/.well-known/jwks.json`), ключи живут в памяти
   процесса. Неизвестный `kid` перечитывает JWKS не чаще раза в
   `auth.jwks_refresh_interval_seconds` (30 с): поток токенов с
   выдуманным `kid` не превращается в поток запросов к `auth`.
2. Подпись RS256, `iss=auth`, `aud=aiip`, срок, обязательные `sub` и `sid`.
3. Пропуск сессии `auth:session:<sid>` в Dragonfly: нет ключа — `401`, кэш
   недоступен — отказ. Так выход и отзыв сессии в `auth` действуют сразу.

`auth` недоступен при старте — сервис всё равно стартует: ключи читаются
при первом запросе. Неизвестный ключ при недоступном `auth` — `503`, а не
`401`: клиент не должен считать, что его разлогинили.

## Права для других сервисов

Решено, но не реализовано — реализуется вместе с первым сервисом, который
проверяет права:

- `projects` — единственный, кто пишет ключ `projects:perm:<project_id>:<user_id>`
  в Dragonfly: набор прав, а не название роли. Пишет сразу после записи
  в БД, отзыв — под блокировкой строки до commit.
- Другой сервис читает этот ключ тем же запросом к кэшу, что и пропуск
  сессии. Ключа нет — внутренний эндпоинт `projects` читает БД и кладёт
  ключ обратно со сроком 5–10 минут. Кэш недоступен — отказ.
- До опоры на эту схему нужно проверить ACL Dragonfly: может ли сервис
  только читать чужие префиксы.

Ключ пока не пишется: без читателя и без эндпоинта восстановления он был
бы непроверенной половиной механизма.

## API-токены проекта

Ключ внешнего мониторинга (`X-Ingest-Key`): Alertmanager, Grafana Alerting
или CI клиента шлют с ним алерты и выкатки. Токен — не участник проекта:
роли у него нет, только `scopes` (`alert.ingest`, `deployment.ingest`).

- Секрет — `aiip_` + `secrets.token_urlsafe(32)`, показывается один раз,
  ответ с ним — `Cache-Control: no-store`. В БД — SHA-256: у случайных 256
  бит перебор невозможен, медленный хэш вроде Argon2 только тратил бы CPU
  на каждый алерт. `prefix` — первые 12 символов, чтобы узнать токен в
  списке.
- Привязка к окружению — составной внешний ключ, как у сервисов.
- Отзыв ставит `revoked_at`, строка остаётся: видно, какой токен когда
  отозван.
- Проверять токен будет сервис приёма алертов. План: `projects` кладёт
  `projects:token:<sha256>` → проект, окружение, scopes в Dragonfly, отзыв
  удаляет ключ до commit под блокировкой строки — как пропуск сессии в
  `auth`. Делается вместе с этим сервисом.

## Данные

- `projects` — `slug` уникален глобально, `archived_at` заведён под
  контракт, архивации пока нет.
- `environments` — `slug` уникален в проекте.
- `monitored_services` — в API `Service`. Составной внешний ключ
  `(environment_id, project_id)` → `environments (id, project_id)`: база
  сама не даст сервису окружение другого проекта. Имя уникально в
  окружении.
- Id — UUIDv7: растут со временем создания, поэтому страница списка —
  `id > курсор ORDER BY id`, а курсор — последний id в base64url.

## Ресурсы и масштабирование

Не замерялось: значения взяты от `auth` с поправкой на лёгкую нагрузку.

- 1–2 пода (KEDA), `maxSurge: 1`: в пике выкатки 3 пода × 10 соединений
  Postgres. Меньше подов, чем у `auth`, — из-за общего бюджета
  `max_connections`.
- `requests` 100m / 160Mi, лимиты 500m / 256Mi.
- Gateway: 50 запросов/с, burst 100 — страница UI делает несколько
  запросов сразу.

## Решения

- **Коннекторы и репозитории — в отдельном сервисе** (2026-10-29). Секреты
  клиентов и ключ GitHub App — в маленьком изолированном сервисе, у
  которого другая работа (вызовы наружу, защита от SSRF, вебхуки) и
  другая нагрузка. Отброшено: всё в `projects` — меньше подов, но баг или
  взлом самого нагруженного сервиса открывал бы код клиентов.
- **Права в Dragonfly, пишет только `projects`** (2026-10-29). Отброшено:
  роли в JWT (контракт запрещает, права устаревали бы на 15 минут);
  запрос к `projects` на каждый запрос (узкое место и общий отказ);
  события в RabbitMQ (у каждого сервиса своя копия прав и своё
  восстановление).
- **Набор встроенных ролей** owner / admin / developer / viewer
  (2026-10-29), таблица выше. Свои роли проекта — позже, колонкой
  `project_id` в `roles` без переделки проверок.
- **Ключи JWKS лениво и с ограничением частоты** (2026-10-30): старт
  `projects` не зависит от `auth`, а неизвестный `kid` не нагружает `auth`.
- **Приглашают только зарегистрированных, принимают сами** (2026-10-30,
  решение пользователя). Человек находится в `users`, письмо — повод зайти
  во входящие. Отброшено приглашение любой почты с созданием аккаунта по
  ссылке: второй путь регистрации мимо `auth`.
- **Профиль спрашивается у `users` с токеном пользователя** (2026-10-30):
  сервисной аутентификации между сервисами ещё нет, а токен приглашающего
  `users` и так принимает. Отброшена копия профилей в `projects` по
  событиям — ради одного письма лишнее состояние.
- **Письмо после commit и без отката** (2026-10-30): приглашение видно в
  интерфейсе и без письма, а публикация до commit держала бы транзакцию
  открытой на время похода в брокер.
